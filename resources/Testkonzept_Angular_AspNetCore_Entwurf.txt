3 Umfang des Testens

3.1 Backend – ASP.NET Core REST-API
Folgende Testkomponenten und Unit-, und Integrationstest dienen als erste Grundlage für
zu testende Bereiche. Diese können sich im Laufe der Entwicklung noch anpassen.
Im reinen Backend wird hauptsächlich mit Unit- und Integrationstests gearbeitet werden.
Weitere Testarten können je nach Bedarf oder Wunsch ergänzt werden.




Abbildung 3 Backend Services - Priorität

GatewayService, ExperimentService und FileService sollten zuerst getestet werden, weil sie
die kritischsten Prozesse der Anwendung abdecken und mit am meisten Daten arbeiten.
Der GatewayService ist der zentrale Einstiegspunkt für das Frontend und prüft
Berechtigungen, der ExperimentService verwaltet die wichtigsten fachlichen Daten wie
Experimente, Tasks und Parameter, und der FileService ist für Upload, Speicherung und
Abruf von Dateien, Bildern und Reports verantwortlich.
Fehler in diesen Services hätten daher besonders große Auswirkungen auf Sicherheit,
Datenqualität und Nutzbarkeit der Anwendung.
Aus diesem Grund werden die Services aus Priorität 1 als erstes abgedeckt.

3.3.1 Backend – End-to-End Tests
  1. GatewayService – Login und Zugriff:
        •   Benutzer wird authentifiziert und ruft das Dashboard über den
            GatewayService auf.
        •   Benutzer mit gültiger Rolle erhält Zugriff auf geschützte Endpunkte.
        •   Benutzer ohne Berechtigung wird abgewiesen oder auf /request-access
            weitergeleitet.
        •   Berechtigungen werden korrekt auf Experimentdaten angewendet.


  2. GatewayService – Experimentdaten geschützt anzeigen:
        •   Benutzer öffnet ein Experiment über den GatewayService.
        •   Der GatewayService lädt die Experimentdaten vom ExperimentService.
        •   Nicht erlaubte Felder werden für den Benutzer ausgeblendet oder ersetzt.
        •   Benutzer sieht nur die Daten, für die er berechtigt ist.


  3. ExperimentService – Experiment anlegen.
        •   Benutzer startet ein neues Experiment.
        •   Benutzer füllt Pflichtfelder wie Titel, Kunde und Verantwortliche aus.
        •   Benutzer speichert das Experiment erfolgreich.
        •   Das Experiment ist anschließend über die Experimentliste abrufbar.


  4. ExperimentService – Experiment Task anlegen.
        •   Benutzer öffnet ein bestehendes Experiment.
        •   Benutzer legt einen neuen Experiment Task an.
        •   Benutzer erfasst relevante Task- und Materialdaten.
        •   Benutzer speichert den Task erfolgreich und sieht ihn im Experiment.


  5. ExperimentService – Setup anlegen und berechnen.
        •   Benutzer legt zu einem Experiment Task ein Setup an.
        •   Benutzer wählt Maschine, Laser, Optik und relevante Parameter.
        •   Benutzer startet die Berechnung.
        •   Benutzer speichert das Setup erfolgreich.


  6. FileService – Datei hochladen.
        •   Benutzer wählt eine Datei oder ein Bild im Experiment aus.
        •   Die Datei wird über den GatewayService an den FileService übertragen.
        •   Der FileService speichert die Datei mit passenden Tags.
        •   Die Datei ist anschließend im Experiment sichtbar und abrufbar

7. FileService – Datei suchen und herunterladen.
      •   Benutzer öffnet die Dateiansicht eines Experiments.
      •   Dateien werden anhand der Experiment-ID gefunden.
      •   Benutzer wählt eine Datei zum Download aus.
      •   Die Datei wird korrekt heruntergeladen.


8. ReportService – Report erzeugen.
      •   Benutzer wählt relevante Parameter und Bilder für einen Report aus.
      •   Benutzer startet die Report-Erstellung.
      •   Der ReportService erzeugt PowerPoint-, Excel- und Bilddaten.
      •   Der fertige Report wird als ZIP-Datei gespeichert und ist abrufbar.


9. ReportService – Report-Vorschau anzeigen:
      •   Benutzer öffnet ein Experiment mit vorhandenem Report.
      •   Die Slide-Preview wird geladen oder neu erzeugt.
      •   Benutzer sieht die Vorschau der Report-Folien.
      •   Fehlerhafte oder fehlende Reportdaten werden verständlich behandelt.


10. SearchService – Suche ausführen:
      •   Benutzer öffnet die Suche.
      •   Benutzer setzt Filter für Material, Parameter oder Messwerte.
      •   Der SearchService liefert passende Suchergebnisse zurück.
      •   Benutzer sieht die Ergebnisse korrekt in der Tabelle.
11. SearchService – Suchfilter speichern:
      •   Benutzer konfiguriert Suchfilter und Tabellenspalten.
      •   Benutzer speichert die Sucheinstellungen.
      •   Benutzer lädt die Suche später erneut.
      •   Die gespeicherten Filter und Spalten werden korrekt wiederhergestellt.

3.3.2 Frontend – End-to-End Tests
  1. Login und Zugriff
        •   Benutzer wird authentifiziert und kann das Dashboard öffnen.
        •   Benutzer ohne Berechtigung wird auf /request-access weitergeleitet.
  2. Experiment anlegen
        •   Benutzer startet ein neues Experiment.
        •   Benutzer füllt Pflichtfelder aus.
        •   Benutzer speichert das Experiment erfolgreich.
        •   Validierungsfehler erscheinen bei fehlenden Pflichtfeldern.
  3. Experiment Task anlegen
        •   Benutzer legt einen Experiment Task an.
        •   Benutzer erfasst relevante Task- und Materialdaten.
        •   Benutzer speichert den Task erfolgreich.
  4. Setup anlegen und berechnen
        •   Benutzer legt ein Setup an.
        •   Benutzer wählt Maschine, Laser und Optik.
        •   Benutzer startet die Berechnung.
        •   Benutzer speichert das Setup.
  5. Parameter bearbeiten
        •   Parameter-Grid wird geladen.
        •   Benutzer fügt eine Parameterzeile hinzu.
        •   Benutzer bearbeitet und speichert die Parameterzeile.
  6. Result erfassen
        •   Benutzer öffnet den Result-Bereich.
        •   Benutzer trägt Ergebniswerte ein.
        •   Benutzer lädt ein Bild oder eine Datei hoch.
        •   Benutzer speichert das Result.
  7. Ungespeicherte Änderungen
        •   Benutzer ändert Daten.
        •   Benutzer versucht die Seite zu verlassen.
        •   Warnung erscheint.
        •   Benutzer bleibt auf der Seite oder bestätigt das Verlassen.
  8. Suche ausführen
        •   Benutzer öffnet die Suche.
        •   Benutzer setzt zentrale Suchfilter.
        •   Benutzer führt die Suche aus.
        •   Benutzer öffnet ein Suchergebnis.

3.4 CI/CD-Pipeline
Für die Anwendung soll es eine Pipeline geben. Im Backend soll es z.B. pro Service eine
eigene Pipeline geben. Diese Pipelines sollen bei Pull Requests automatisch ausgeführt
werden, sodass Änderungen frühzeitig geprüft werden können, bevor sie gemerged werden.
Aktuell sind die Pipelines jedoch deaktiviert. Wichtig ist außerdem, dass es sich dabei nicht
um reine Test-Pipelines handelt: Neben Tests können dort auch weitere Schritte wie Build,
Analyse, Packaging oder Deployment-Vorbereitung enthalten sein. Am Ende der Pipeline
können Agents eingesetzt werden, die die jeweiligen Pipeline-Schritte ausführen und die
Ergebnisse bereitstellen.
